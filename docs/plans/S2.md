# S2 · Moves (ledger, five passes, explanations) Implementation Plan

> **For agentic workers:** You are session **S2** of 5 parallel Claude sessions. REQUIRED SUB-SKILL: superpowers:executing-plans (implement inline, no subagents). Steps use `- [ ]` checkboxes. Don't stop to ask unless truly blocked; make the reasonable call and note it in the commit message.

**Goal:** Turn features into the ranked, rule-respecting, explained move list (contract C2 `groups` + `problems`).

**Architecture:** `engine/moves.py::generate_moves(data, feats)` builds a `Ledger` of projected stock, runs five allocation passes that read and write the ledger (so nothing is double-counted and every rule is checked at allocation time), groups SKU lines into approvable style-level groups, clusters groups into headline problems, and calls `engine/explain.py` for one-line reasons. `engine/run.py` (S0) already calls you via `engine/interfaces.generate_moves`.

**Tech Stack:** Python 3.12, pandas, numpy, pytest.

**Spec:** `docs/superpowers/specs/2026-11-21-stock-mover-design.md` (§2 rules, §5.5–5.8, §5.10) and `contracts/CONTRACTS.md` (C1, C2). Example output: `contracts/sample_run.json`. Read `engine/data.py`, `engine/interfaces.py`, `engine/naive.py`, `engine/config.py`, `engine/run.py` first.

- Hard rules (enforce in the ledger; S3's validator re-checks independently, `python -m engine.run` without `--no-strict` refuses to publish on any violation):
  1. Giver store's category-group total (`cat_group`; accessories already merged) never drops below `data.min_display` for its tier.
  2. S++ store never gives a protected style (`engine.data.protected_styles(data)`), any size, any move type.
  3. Receiver store total (`available` + inbound moves − outbound moves) never exceeds `stores.capacity`. A store already over capacity (KNP-03) receives nothing.
  4. `available` already includes `in_transit`; never send to a store×SKU whose `available` already meets its target.
  5. STORE_TO_STORE only if giver's **style-level** cover after the move ≥ 30 days (`Σ available / Σ vel_daily` over that style's SKUs at the giver; vel 0 → infinite cover → OK).
  6. `needs_approval = mrp_value > 100000` (flag only).
- Dates: `ship_on` for store-origin moves = `as_of + 1 day` (2026-11-01). WH sends ship on the earliest date the WH has the units (`wh_timeline.cum_qty` minus what you already allocated): `as_of + 1` if on hand, else that inbound date. `arrives_on = ship_on + lead_days(from, to, data.stores)`.
- Group = (type, problem_kind, from, to, style_id). `sizes` dict ordered by size, `lines` one per SKU.
- Explanations: one line, ≤ 220 chars, numbers only from ledger/features, format `"<FROM> → <TO> · <qty> × <STYLE> (<sizes>): <reason with ≥2 numbers>"`. WH shown as `WH`.

## Review Focus
- A SKU needed by 15 stores with 190 units arriving (KUR-01): every selling store gets a presentation minimum before any store is topped up; no store gets more than its need.
- Giver whose category is exactly at min display: it can give 0 of that category.
- Stock that is both "excess" at a donor and "aged": move it once (ageing pass must not re-move stock already moved).
- A SKU sent to a store must never also be pulled from that store in the same run (round trip).
- WH supply arriving 16 Nov for a South store (6-day lead) arrives 22 Nov — still before the 12 Dec season end, so allowed; supply arriving 16 Dec is useless for ageing moves (`arrives_on > SEASON_END` → skip for AGEING).

Else: (a) 1 unit to every store whose need > 0 and `vel_daily > 0`, highest vel first, until supply runs out; (b) the rest in proportion to remaining `need_units × vel_daily` (largest remainder).
